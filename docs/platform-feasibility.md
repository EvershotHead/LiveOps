# 多平台数据源可行性探测报告

> 探测时间：2026-09-11 · 探测人：开发 Agent（强模型层）
> 目的：回答「小红书 / 抖音 / 微博 / 米游社 能否作为 LiveOps 后续数据源」，区分三种结论：
> **A 公开可读**（无需登录）/ **B 需要登录** / **C 需要签名或反爬层（非登录问题）**。
> 合规边界：每平台 ≤10 个温和 GET 请求、桌面/移动 UA、无登录、无签名伪造、遇到登录墙或
> 风控码即停止并记录，不重试不绕过。与 `docs/compliance.md` 红线一致。

## 一、结论速览

| 平台 | 结论 | 墙的类型 | 后续接入建议 |
|---|---|---|---|
| **米游社** | **A · 公开可读** | 无（游客可读全部公开帖） | **优先接入**：官方社区、口径干净、合规风险最低 |
| **微博** | **B+ · 游客可浏览，登录更好** | 官方游客系统（自动放行）+ 未登录限流 | 第二顺位：浏览器游客态可采，登录账号后搜索 API 更稳、限流更松 |
| **小红书** | **B · 强制登录** | 登录墙（302 → /login）+ API 签名（x-s/x-t） | 暂缓：必须登录账号，且登录后仍需真实浏览器环境执行签名 |
| **抖音** | **C · 反爬签名墙** | X-Bogus/msToken/a_bogus 签名 + JS 虚拟机壳 | 暂缓：非登录能解决的问题，自动化采集需要逆向签名（属绕过行为，不做） |

## 二、逐平台证据

### 1. 米游社（miyoushe.com）— 公开可读 ✅

- 首页 HTML 正常返回（200），无登录墙。
- **帖子流**：`bbs-api-static.miyoushe.com/apihub/wapi/webHome?gids=2&page=1&page_size=20` → 200，
  返回推荐帖完整结构（`post_id / subject / content 正文 / created_at / 用户昵称与认证 / 话题标签`）。
- **帖子详情**：`bbs-api.miyoushe.com/post/wapi/getPostFull?gids=2&post_id=<id>` → 200（含嵌套 `post.post` 结构）。
- **回复列表**：`bbs-api.miyoushe.com/post/wapi/getPostReplies?gids=2&is_hot=true&post_id=<id>&size=20`
  → 200，返回 `data.list[]` + `data.last_id` 翻页游标 + `data.total_reply_num`。
  实测样例帖（7.0 问题集中反馈帖）`total_reply_num=2931`，第 1、2 页各返回 18/19 条，`last_id` 递增翻页正常。
- 探测中同样暴露的细节：`getPostReplies` 必须带 `is_hot` 参数（不带报「不支持的排序类型」）；
  回复正文字段不在顶层（接入时需适配嵌套结构）；站内搜索接口路径与旧文档不同，接入时需从网页抓包确认。
- **判定**：游客态即可完整读取公开帖与回复。注意 `stat`（点赞/阅读数）在游客响应里可能恒为 0，
  互动量指标接入前需抽样验证。

### 2. 微博（weibo.com / m.weibo.cn）— 游客可浏览，登录更好 ⚠️

- 桌面端热搜 API `weibo.com/ajax/side/hotSearch` → **403 Forbidden**（需登录 cookie）。
- 移动端直接调 `m.weibo.cn/api/container/getIndex?containerid=100103type=1&q=…` → **432**（需验证）。
- **官方游客系统（Sina Visitor System）**：浏览器访问 `m.weibo.cn` 任意页会跳转
  `visitor.passport.weibo.cn/visitor/visitor?a=enter…`，官方 JS 数秒内自动完成游客身份发放并回到原页——
  这是平台为未登录用户设计的公开访问路径，不涉及绕过。
- 实测（Playwright 无痕浏览器，模拟未登录用户）：自动通过游客系统后搜索「原神7.0」
  返回 22 张卡片，`getIndex` API 200，微博正文可读（含 #原神7.0# 话题内容）。
- 旧的 `passport.weibo.cn/visitor/genvisitor` 手工游客端点现已返回 HTML（接口形态已变），
  纯 HTTP 复刻游客 cookie 流程需要重新抓包分析。
- **判定**：浏览器环境下游客即可浏览与搜索；自动化采集建议两条路——(a) 浏览器 RPA 游客态（成本中等，限流未知）；
  (b) **登录账号**后直接调 `getIndex` 等 API（更稳、翻页更深），用户已有微博账号即可。

### 3. 小红书（xiaohongshu.com）— 强制登录墙 🚫

- `GET /explore` → **302 重定向到 `/login?redirectPath=…`**：未登录不给任何内容流。
- 搜索 API（edith 网域）无签名请求 → 404/拒绝；已知该 API 需要 `x-s / x-t` 请求签名（由前端 JS 生成）。
- **判定**：双重门槛 = 登录账号 + 签名层。签名由页面 JS 动态生成，纯 HTTP 无法构造；
  即便登录，采集也需要真实浏览器环境（RPA）。**如果后续要接：必须提供登录账号**，
  且建议以浏览器自动化方式温和采集（低频、仅公开笔记），工程与风控成本都显著高于微博。

### 4. 抖音（douyin.com）— 反爬签名墙，与登录无关 🚫

- 搜索 API `aweme/v1/web/search/item/` 无签名请求 → HTTP 200 但 **`aweme_list: null`**
  （静默空响应，无签名不报错、只返回空——典型的签名前置校验）。
- 页面 HTML 是 **JS 虚拟机混淆壳**（`_$jsvmprt` 运行时），真实内容完全依赖浏览器内执行的
  acrawler 指纹与 `X-Bogus / msToken / a_bogus` 签名链。
- **判定**：这不是登录问题（登录也不解决签名），而是平台反爬设计。构造合法签名需要逆向其
  混淆 JS——**属于绕过风控，超出本项目合规边界，不做**。抖音数据的唯一合规路径是
  官方开放平台/合作协议，或人工合规导出。

## 三、对后续项目发展的建议

1. **第二数据源首选米游社**：游客全可读、官方社区（内容质量高、与游戏运营直接相关）、
   结构化数据完整（帖子 + 回复 + 话题标签 + 官方认证标识）。接入工作量约等于复刻现有 B 站采集器的
   `collector/miyoushe.py`，Schema 侧只需给 `CommunityPost` 增加 `platform` 字段（现为 B 站默认）。
   注意合规细节：昵称/UID 照旧 HMAC 匿名化；游客态互动数可能为 0 需另证。
2. **微博作为第三顺位**：需要用户提供一个登录账号（哪怕小号）收益最大；游客 RPA 也可行但限流口径未知。
3. **小红书仅在提供登录账号并接受浏览器 RPA 成本时考虑**；建议先人工评估内容价值再决定。
4. **抖音建议放弃自动采集**，若确有需要走官方开放平台。

## 四、方法附注

- 探测工具：`backend/tools/probe_platforms.py`（httpx 温和 GET）+ Playwright 无痕浏览器（模拟未登录用户）。
- 原始响应摘录：`backend/probe_results.json`（本地，不入库敏感信息）。
- 所有探测均为只读公开接口，未登录任何账号，未伪造签名，未重试风控响应。
