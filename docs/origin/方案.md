# LiveOps Community Intelligence 完整项目方案

## 一、项目定位

项目名称暂定为：

**LiveOps Community Intelligence：游戏版本社区洞察与运营复盘系统**

代码仓库建议命名为 `liveops-community-intelligence`，默认项目目录为 `D:\AllAI\LiveOpsCommunityIntelligence`。

它不是通用情感分析工具，也不是“把评论全部交给大模型总结”的套壳应用，而是一套面向游戏版本运营的、可复现且可审计的分析流程：

> 公开社区数据 → 规范化 → 游戏运营标签识别 → 人工与模型复核 → 量化聚合 → 原文证据回溯 → 版本复盘与运营建议

目标用户包括游戏运营、社区运营、市场营销、用户研究和产品策划人员。作为个人作品，它需要同时证明游戏理解、社区运营思维、数据分析能力和 AI Agent 工程能力。

已锁定的 MVP 决策：

- 首批对照游戏：《原神》与《鸣潮》。
- 首批只分析 B 站，避免一开始被多平台口径拖垮。
- 展示模式为“公开预计算演示站 + 本地完整分析系统”。
- 第一版分析文本、视频元数据和公开互动量，不分析视频画面、语音和图片。
- 后续优先扩展 TapTap，再考虑贴吧、米游社、库街区和小红书。

## 二、成功标准

项目完成后，应当让 HR 或业务面试官在不配置模型密钥的情况下打开演示站，看到两个真实版本案例、分析结果、样本口径、原文证据、模型评测和项目方法。

本地运行时，用户可以导入 CSV、XLSX、JSON 或 JSONL 数据，经字段映射后创建分析任务，得到仪表盘和版本复盘报告。

核心验收标准：

- 《原神》《鸣潮》各分析一个符合条件的大版本，每款游戏不少于 3,000 条有效评论，目标为 4,000-5,000 条。
- 每款游戏覆盖 40-60 个相关视频，任何单一视频不得贡献超过该游戏样本的 10%。
- 所有重要结论都能回溯到统计口径和代表性原文，不允许只有 AI 总结。
- 所有运行记录模型、提示词版本、代码版本、数据集哈希、参数、成本和时间。
- 公开演示数据删除用户名和个人资料字段，对用户标识进行不可逆匿名化。
- 主要标签达到预设评测门槛，模型无法判断时允许弃权，不伪造准确率。

## 三、案例与数据方案

每款游戏选择截至采集日“最近一个已经上线至少 28 天”的大版本。该版本还需满足 B 站至少能定位 40 个有效视频和 3,000 条有效评论；若不满足，自动退回上一个大版本。

统一采用相对版本时间窗口：

- `T0`：版本正式更新时间。
- 预热期：`T-7` 至 `T-1`。
- 上线期：`T0` 至 `T+7`。
- 发酵期：`T+8` 至 `T+28`。

视频样本分为官方物料、攻略解析、体验评价、二创内容、争议或问题讨论五类。通过官方视频种子、游戏名、版本名、角色名、活动名和问题关键词构建检索清单，并保存检索词、检索时间、结果排名和采样原因。

评论采样同时覆盖热门评论、时间序列评论和楼中楼回复，避免只分析点赞最高的观点。需要限制单视频、单作者和复制文本的影响，对抽奖、广告、无意义刷屏、重复评论和完全无关内容进行单独标记。

数据获取遵守以下底线：

- 仅处理公开可见内容，不绕过登录、验证码、风控或平台访问限制。
- 设置速率限制、失败退避、断点续采和采集日志。
- 如果自动采集不符合平台规则或稳定性不足，立即切换为“视频 URL 清单 + 合规导出数据”模式。
- 产品核心不能依赖爬虫才能运行，导入用户自有数据必须是正式能力。
- 公开演示仅展示匿名化文本片段和来源视频链接，不公开用户主页、头像、UID 或其他个人资料。

## 四、Canonical Schema

导入数据最少需要 `text`、`published_at` 和 `source_url`。系统提供 AI 字段映射建议，但必须由用户确认，随后再通过固定 Schema 校验。

核心数据对象包括：

- `StudyConfig`：游戏、版本、T0、时间窗口、关键词、样本配额和分析模板。
- `ContentItem`：视频 ID、标题、URL、发布时间、内容类型、作者类型、播放/点赞/评论等快照指标。
- `CommunityPost`：评论 ID、父评论、正文、时间、点赞、回复数、匿名用户 ID、采集时间和去重组。
- `Annotation`：相关性、主题、立场、情绪、强度、反讽、表达意图、问题类型、置信度、证据片段和弃权原因。
- `AnalysisRun`：数据集哈希、配置、模型、提示词版本、代码提交、状态、错误、成本和运行耗时。
- `HumanReview`：人工修改前后标签、修改原因、审核人和审核时间。

第一版不直接接受任意 SQL 连接；只读 SQL 数据源留作扩展功能，防止范围失控。

## 五、游戏运营标签体系

主题采用多标签体系，初始固定为 12 类：角色设计与美术、战斗与玩法、剧情与世界观、地图与探索、版本内容量、活动设计、养成与资源、抽卡与商业化、平衡与强度、性能与缺陷、界面与便利性、官方沟通与社区生态。无法归入既有类别的内容进入“新兴主题”，通过语义聚类发现后再人工命名。

其他标签定义：

- 立场：支持、反对、中立、混合、不明确。
- 情绪：喜悦、期待、惊讶、失望、愤怒、焦虑、调侃/玩梗、无明显情绪。
- 情绪强度：0-3。
- 反讽：无、可能、明显、无法判断。
- 表达意图：称赞、体验陈述、问题报告、改进建议、提问、玩梗、冲突回应、传闻讨论。
- 问题性质：内容不足、设计分歧、数值争议、技术故障、奖励争议、沟通问题、社区冲突、其他。
- 置信度：0-1，并保留简短证据片段；不保存或展示模型内部思维过程。

网络梗、反串、引用他人和语境不足的内容不得被强行二分。低置信度、高互动量、明显反讽和争议核心样本必须进入强模型或人工复核队列。

## 六、分析方法与指标

系统不以单一 `-10 至 10` 情感分数代表社区倾向，而是分别展示：

- 主题占比：某主题评论数除以有效评论数。
- 净支持率：`(支持数 - 反对数) / (支持数 + 反对数)`，并同时显示中立和混合样本。
- 争议度：立场分布熵、回复冲突程度和讨论量的组合。
- 趋势速度：某主题在相对版本时间中的新增速度和变化率。
- 互动影响：经 `log1p` 处理后的点赞、回复和视频覆盖量。
- 持续性：问题跨多个日期和多个视频持续出现的程度。
- UGC 扩散：相关视频数量、内容类型覆盖和讨论增长，不将播放量直接等同于口碑。
- 运营问题优先级：反对强度 30%、主题占比 25%、增长速度 20%、互动影响 15%、持续性 10%。
- 正向机会值：支持率 35%、主题增长 25%、视频覆盖 20%、互动影响 10%、持续性 10%。

组合权重是可配置的运营排序规则，不包装成客观真理。仪表盘必须展示各项分量，并提供权重敏感性对比。

双游戏对照只在相同相对时间窗口和相近抽样口径下进行，使用“每千条评论”“每十个视频”等归一化指标。产品不得输出简单的“哪款游戏更好”，而应比较版本亮点、问题结构、讨论节奏和社区关注差异。

## 七、AI Agent Harness

分析系统采用受约束的工作流，而不是让一个自主 Agent 随意决定分析过程：

1. 数据映射与 Schema 校验。
2. 文本清洗、去重、语言判断和表情符号规范化。
3. 相关性过滤。
4. 中文语义向量聚类与新兴主题发现。
5. 低成本模型执行结构化标签任务。
6. 低置信度、反讽、高互动和冲突样本路由至强模型复核。
7. 人工审核关键样本与模型分歧。
8. Python 代码完成统计聚合，禁止让 LLM 计算最终指标。
9. 报告 Agent 只能读取结构化指标和证据集合，每条结论必须引用指标 ID 与证据 ID。
10. 验证节点检查结论是否超出样本范围、是否缺少证据、是否把相关性写成因果。

提示词、少样本示例、JSON Schema 和路由规则全部版本化。社区文本一律视为不可信输入，用明确的数据边界包裹，并声明不得执行文本中包含的指令，以防提示词注入。

## 八、技术架构与界面

推荐技术栈：

- 前端：Next.js、TypeScript、Tailwind CSS、shadcn/ui、Lucide、ECharts。
- 后端：FastAPI、Pydantic、Polars、DuckDB、Parquet。
- AI 工作流：LangGraph 或等价的有状态图工作流；中文向量默认使用 `bge-m3`。
- 模型接口：兼容 OpenAI 风格的 `base_url/api_key/model` 配置，并预留 Ollama 适配器。
- 测试：Pytest、Vitest、Playwright。
- 部署：公开演示站读取预计算 JSON；本地完整模式通过 Docker Compose 或一键脚本启动前后端。

每次运行使用独立目录保存 `manifest.json`、规范化数据、模型标注、人工覆盖记录、聚合指标和报告。分析任务单机串行运行，支持阶段级断点续跑，不引入 Redis、Celery或多租户权限系统。

主要页面：

- 数据与任务：文件导入、字段映射、版本配置、任务进度、失败重试和成本预估。
- 总览：数据覆盖、主题分布、正负向信号、风险与机会列表。
- 版本时间线：以 T0 为中心展示主题、情绪和争议变化。
- 主题洞察：筛选主题、角色、活动、视频类型、时间和立场。
- 社区争议：展示冲突话题、观点矩阵、回复链强度和代表性证据。
- 双游戏对照：归一化比较《原神》和《鸣潮》，同时显示样本差异提示。
- 证据与审核：原文片段、来源链接、模型标签、置信度、人工修正和导出。
- 模型评测：Macro-F1、混淆矩阵、弃权率、校准、成本和吞吐量。
- 运营报告：版本亮点、主要问题、社区诉求、建议动作、证据和局限性。

界面应是安静、紧凑的运营工作台，不制作营销落地页，不堆叠装饰卡片。公开演示为只读，本地模式才显示导入、模型配置和人工审核功能。

## 九、评测、测试与验收

建立至少 800 条人工金标准样本，每款游戏 400 条；其中不少于 20% 由两名人工独立标注。主要标签 Cohen’s Kappa 目标不低于 0.70。

模型目标：

- 相关性 Macro-F1 ≥ 0.90。
- 主题多标签 Macro-F1 ≥ 0.70。
- 立场 Macro-F1 ≥ 0.75。
- 情绪 Macro-F1 ≥ 0.65。
- 反讽 Macro-F1 ≥ 0.60，同时报告弃权率。
- 高优先级运营结论 100% 经过人工复核。

训练与测试按视频分组切分，避免同一评论区同时出现在训练集和测试集。若人工标签不足 1,500 条，第一版不得宣称完成了可靠微调；先采用 LLM 结构化标注、向量基线和人工复核。

测试必须覆盖文件解析、字段映射、去重、时间窗口、指标公式、异常模型输出、任务恢复、提示词注入、损坏文件、空数据、超大文本、API 限流和密钥缺失。Playwright 检查公开演示与本地模式的桌面和移动端页面，不得出现空图、文字重叠或不可点击证据链接。

## 十、实施阶段

- P0，2-3 天：PRD、标签手册、Schema、版本选择与采样协议定稿。
- P1，5-7 天：仓库骨架、文件导入、规范化、100 条固定样本的纵向切片。
- P2，7-10 天：B 站数据整理、双游戏样本冻结、800 条人工标注和一致性检验。
- P3，5-7 天：分层模型路由、评测、指标计算、证据链和报告生成。
- P4，7-10 天：完整前端、本地分析模式、公开预计算演示。
- P5，3-5 天：安全审计、视觉 QA、部署、README、演示视频和案例报告。

项目达到 P4 即可作为简历作品；P5 完成后再正式写入量化成果。不得提前虚构评论数量、准确率或业务效果。

最终交付物包括 GitHub 仓库、公开演示地址、匿名化案例数据、标签手册、模型评测报告、两个版本复盘报告、架构图、数据合规说明、2-3 分钟操作视频，以及适合简历使用的三条量化项目描述。

## 十一、明确不做

第一版不做实时全网监控、不绕过平台风控、不做用户画像、不做舆情操纵预测、不分析视频画面、不自动微调无标签数据、不做通用 Agent 测评平台，也不声称 B 站样本代表全体玩家。

第二阶段优先接入 TapTap，并分别展示平台结果、采样归一化结果和平台差异；不得将不同平台原始数量直接混合。积累 1,500-3,000 条可靠人工标签后，再评估 MacBERT、RoBERTa 或语义向量分类器，以降低全量 LLM 成本。
